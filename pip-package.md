# Proposal: a `pip` package for MGIS (issue #254)

Status: proposal, to be discussed on the issue before implementation.

Scope of the first version: **python bindings only** (no C / Fortran / FEniCS /
Julia bindings in the wheel), **portable build**
(`-Denable-portable-build=ON`), TFEL support **fully enabled**
(`MGIS_HAVE_TFEL`, `MGIS/Function` + precompiled operations, MFront
database, TFEL python bindings), **stubs generated with
`pybind11-stubgen`** as in TFEL (PR thelfer/tfel#1083).

The wheels are built by a GitHub Actions workflow modeled on TFEL's
`.github/workflows/python-pip.yml`, with `pypa/cibuildwheel`.

---

## 1. Reference: what TFEL already does

- `bindings/python/pip/{pyproject.toml,setup.py,test_wheel.py}`: `setup.py`
  configures, builds and installs TFEL with cmake, then lays the
  installation out as a python package. The `tfel` module *is* TFELHOME:
  `bin`, `lib`, `include` and `share` are placed inside it, and a short
  preamble inserted into the `__init__.py` scripts sets the
  `TFELHOME_<version>` environment variable, which TFEL's
  `GetInstallPath.cxx` honours with priority over `TFELHOME`.
- `set_relative_runtime_paths()` rewrites the runtime path of every binary
  of the wheel to be relative to `tfel/lib` (`patchelf --force-rpath`,
  hence `DT_RPATH`, on purpose: it is searched before `LD_LIBRARY_PATH`;
  `install_name_tool` + `codesign --force --sign -` on macOS; nothing on
  Windows, where `__init__.py` calls `os.add_dll_directory`).
- Windows wheels: `repair-wheel-command = ""`, since delvewheel would copy
  the TFEL DLLs under other names, so a behaviour loaded in python would
  load a second copy of them.
- `.github/workflows/python-pip.yml`: cibuildwheel over
  ubuntu/macos/windows x cp39…cp315 (cp312 only on pull requests), ccache
  (one cache per OS, saved by the cp312 job; static musl ccache inside the
  manylinux container, `CCACHE_DIR=/host<runner.temp>/ccache`), publish to
  PyPI and to the GitHub release on the `TFEL-x.y.z` tags.

### Lessons of the review of TFEL PR #1083 (pybind11-stubgen)

The same exercise is done for MGIS, so MGIS starts from the *reviewed*
design, not from the first proposal of PR #1083:

1. `pybind11-stubgen` is **looked for and run with `${Python_EXECUTABLE}`**
   (`${Python_EXECUTABLE} -c "import pybind11_stubgen"`, then
   `${Python_EXECUTABLE} -m pybind11_stubgen <module>`), never searched in
   the `PATH`: the stubgen tool must import the modules, hence run with the
   interpreter they are built for. If it is not available for this
   interpreter, the stubs are simply not generated (the stubs are
   optional, they shall never break a build).
2. **Multi-configuration generators** (Visual Studio) append the
   configuration name to the output directory of the modules
   (`mgis/Release/_mgis.pyd`), whereas `__init__.py` of the package is in
   `mgis/`: importing the package from the build tree fails, which breaks
   the stub generation on Windows. Fix (thelfer/tfel@e0e5a81): hold the
   output directories in a generator expression, e.g.
   `"$<1:${dir}>"`, so that no subdirectory is appended. Accepted
   trade-off: with such a generator, the modules of the configurations
   built in the same build directory overwrite each other, which is
   already the case for the python tests (disabled with
   multi-configuration generators).
3. `os.add_dll_directory` shall only be called on **existing** directories
   (thelfer/tfel@969e4ed): the `__init__.py` scripts run when the modules
   are imported from the build tree, where the `bin` directory does not
   exist. (MGIS: `__init__.py` and `__init__-have-tfel.py` already guard
   with `os.path.isdir`, nothing to do.)
4. On Windows, importing the modules from the build tree needs the
   directories of the DLLs of the build tree (python ignores `PATH` since
   3.8): a **`sitecustomize.py`**, generated by cmake and placed in a
   directory added to the `PYTHONPATH` used to run pybind11-stubgen, calls
   `os.add_dll_directory` on those directories, determined from a global
   property listing the libraries created by `mgis_library` (TFEL uses the
   `TFEL_LIBRARIES` property, which required adding one
   `set_property(GLOBAL APPEND …)` to `tfel_library_internal`).
5. The stubs are generated by a `python-stubs` target, built with the
   project, and installed **next to the modules** they describe.
6. `pybind11-stubgen` is pinned to `>=3.0` in the pip build requires (the
   versions below 3 are not tested).
7. `test_wheel.py` checks that the stubs are installed.
8. `py.typed`: agreed in the review (PEP 561: type checkers ignore the
   stubs of an installed package without this marker), to be installed as
   an empty file in each python package — not committed in TFEL yet;
   MGIS shall install it too so that both packages are consistent.

## 2. The hard part: consistency between the MGIS and TFEL wheels

MGIS links `tfel::TFELMath` and `tfel::TFELMFrontDatabase` **PUBLICLY**, and
`MGIS_HAVE_TFEL` is a PUBLIC compile definition: TFEL is part of the ABI
MGIS exposes to its own consumers (and the python bindings import
`mfront.database`). A MGIS wheel must therefore be paired with one, and
only one, TFEL wheel.

### 2.1 Candidate designs

- **A. Vendor TFEL** (build TFEL from sources inside the MGIS wheel):
  rebuilds all of TFEL for every python x OS cell, and duplicates the
  content of `tfel-mfront` → two wheels owning the `tfel` python package,
  one silently overwriting the other. **Rejected.**
- **B. Depend on the published `tfel-mfront` wheel as a build *and* run
  dependency, pinned to the exact same version.** **Chosen.**
- **C. Build against TFEL workflow artifacts**: same pin problem as B and
  no longer needed once `tfel-mfront` is on PyPI. Kept only as an escape
  hatch (`CIBW_BEFORE_BUILD` installing a wheel from a URL) while
  `tfel-mfront` is not published, which is the case today (pypi.org
  answers 404 for `tfel-mfront`). **Rejected as the primary mechanism.**

### 2.2 Design B: five complementary layers

1. **One source of truth for the TFEL pin**: `TFEL_DEPENDENCY =
   "tfel-mfront==X.Y[.Z]"` is a constant of `setup.py`; the pin is written
   twice in `pyproject.toml` (`[build-system].requires` and
   `[project].dependencies`) because `pyproject.toml` cannot compute it,
   and `setup.py` raises if the two literal pins of `pyproject.toml` do not
   match the constant. Bumping the pin is one edit + its copy.
2. **Build time**: `[build-system] requires = [..., "tfel-mfront==…"]` puts
   a complete TFEL installation in pip's isolated build environment.
   `setup.py` locates it with
   `importlib.util.find_spec("tfel").submodule_search_locations[0]`
   (no import, no library load) and configures MGIS with
   `-DTFEL_DIR=<tfel>/share/tfel/cmake` (+ `TFELHOME` in the environment),
   `-Drequire-tfel=ON` and `-DMGIS_REQUIRED_TFEL_VERSION=<pin>`. The TFEL
   wheel layout (`tfel/{bin,lib,include,share/tfel/cmake}`) is exactly what
   MGIS's `FindTFEL.cmake` consumes.
3. **Configure-time assertions** (cmake changes, §4.2): the configuration
   fails if TFEL is not found, if `MGIS_HAVE_MFRONT_SUPPORT` is off, if
   `TFEL_PYTHON_BINDINGS` is off (the wheel needs `mfront.database`), or if
   `TFEL_VERSION` differs from `MGIS_REQUIRED_TFEL_VERSION`. A wheel can
   never be produced against the wrong TFEL.
4. **Run time**: `[project] dependencies = ["tfel-mfront==…"]` makes pip
   install exactly the TFEL wheel MGIS was built against, and the preamble
   inserted in `mgis/__init__.py` (pip variant, §4.3) checks at import
   `importlib.metadata.version("tfel-mfront")` against the version baked in
   at build time, and raises a clear `RuntimeError` on mismatch. This
   matters because the TFEL wheel has **unversioned libraries**
   (`-Dunversioned-libraries=ON`): `DT_NEEDED = libTFELMath.so` with no
   soname version, so the dynamic loader cannot tell two TFEL versions
   apart and would fail with an obscure `ImportError` much later.
5. **End-to-end proof in the job**: `test_wheel.py` (§5) compiles a
   behaviour with the `mfront` of the TFEL wheel, loads it with
   `mgis.behaviour.Behaviour` and integrates it, checks the TFEL versions
   agree and the stubs are installed. A wrong toolchain/ABI/glibc
   combination fails before publishing.

### 2.3 Toolchain consistency and determinism

The MGIS wheel links the TFEL libraries, so it must be built with the same
compiler and target as `tfel-mfront`:

- Linux: same cibuildwheel manylinux image (`skip *-musllinux_*`,
  `archs = ["x86_64"]`). The image shall be pinned explicitly
  (`CIBW_MANYLINUX_X86_64_IMAGE`) in **both** projects so they cannot drift.
- macOS: `MACOSX_DEPLOYMENT_TARGET=11.0`, `archs = ["arm64"]` (as TFEL).
- Windows: same runner image (hence same MSVC), `archs = ["AMD64"]`.

Release order: the TFEL wheels must be on PyPI first; add
`workflow_dispatch` to the MGIS workflow and document the order.

Determinism — silent variation is a consistency bug too. `setup.py` shall
set **all** the options explicitly, in particular:

```
-DCMAKE_BUILD_TYPE=Release            -Denable-python-bindings=ON
-Denable-portable-build=ON            -Denable-testing=OFF
-Denable-website=OFF                  -Denable-doxygen-doc=OFF
-Denable-c-bindings=OFF               -Denable-fortran-bindings=OFF
-Denable-fenics-bindings=OFF          -Denable-julia-bindings=OFF
-Denable-cuda-algorithms=OFF          -Denable-openmp=OFF
-Denable-exceptions=OFF               -Ddisable-tfel=OFF
-Denable-hdf5-support=OFF             -Denable-hdf5-automatic-support=OFF
-Drequire-tfel=ON                     -Denable-pybind11-stubgen=ON
-DMGIS_PYTHON_MODULES_INSTALL_DIRECTORY=site-packages
-DPython_EXECUTABLE=<sys.executable>  -Dpybind11_DIR=<copied pybind11>
```

`enable-hdf5-automatic-support=OFF` is essential: otherwise the content of
the wheel silently depends on whether HDF5 happens to be present in the
container. `pybind11` is copied to a fixed path (as in TFEL) so that the
changing paths of the isolated build environments do not defeat ccache.
OpenMP: OFF for v1, as in TFEL's pip build (it would tie the wheel to the
toolchain's `libgomp`); documented as a limitation.

## 3. Wheel layout

The `mgis` module plays the role of MGISHOME, exactly as the `tfel` module
is TFELHOME in `tfel-mfront`:

```
mgis/                       # python package + MGISHOME
  __init__.py               # pip variant (see §4.3)
  _mgis.cpython-3XX-*.so/.pyd
  behaviour.*  material_property.*  model.*  function.*
  *.pyi                     # stubs            + py.typed
  lib/  (Windows: bin/)     # libMFrontGenericInterface…
  include/MGIS/…            # MGIS headers      (decision: ship them)
  share/mgis/cmake/…        # so that find_package(MFrontGenericInterface)
                            # also works from the wheel
```

`MGIS_APPEND_SUFFIX` is not used by the wheel (the package is `mgis`; the
PyPI name **`mgis` is available** — pypi.org answers 404 as of 2026-11-06 —
which is the natural name; alternative if disputed:
`mfront-generic-interface`).

MGIS installs **no executables**, so no launcher module is needed: `mfront`,
`mtest` and `tfel-config` come from the `tfel-mfront` dependency's console
scripts.

### Runtime paths (`set_relative_runtime_paths`, adapted from TFEL)

Every ELF/Mach-O binary of the wheel gets a **relative** runtime path,
computed with `os.path.relpath` from its own directory to **both**:

- `mgis/lib` (`mgis/bin` on Windows, irrelevant on ELF/Mach-O anyway), and
- the `lib` directory of the **sibling `tfel` wheel**, i.e.
  `site-packages/mgis/lib/../..` → `site-packages/tfel/lib`
  (`$ORIGIN/../../tfel/lib`, `@loader_path/../../tfel/lib`). The relative
  path must be computed from the *installed* position: the root of the
  wheel becomes `site-packages`, whereas the build directory of the package
  is an arbitrary other directory, so the computation is done on simulated
  `site-packages/mgis/...` paths. Computing it from the build tree gives a
  path off by one level (which local tests may mask through
  `LD_LIBRARY_PATH`).

Linux: `patchelf --force-rpath --set-rpath` (`DT_RPATH`, searched before
`LD_LIBRARY_PATH`, as in TFEL); the rpath is a `:`-separated list of both
directories. macOS: `install_name_tool -delete_rpath/-add_rpath` +
`codesign --force --sign -`. Windows: nothing; the pip `__init__.py`
registers `mgis/bin` **and `tfel/bin`** with `os.add_dll_directory`
(importing `mgis` does not necessarily run `tfel/__init__.py`, and
MGIS's DLLs need TFEL's DLLs).

### Avoiding re-vendoring TFEL (repair step)

auditwheel (linux) and delocate (macOS) **vendor the libraries the wheel
needs which are not inside it** — that would copy the TFEL libraries of the
sibling wheel into the MGIS wheel under mangled names, and a behaviour
would then load two copies of TFEL (the exact failure TFEL disables
delvewheel for). The repair step must therefore *exclude* them:

- linux: `CIBW_REPAIR_WHEEL_COMMAND = "auditwheel repair -w {dest_dir}
  {wheel} --exclude <pattern> …"`. Since auditwheel 6, `--exclude` is a
  **glob** (`fnmatch`), not a regex: `libTFEL.*` silently matches nothing
  and the TFEL libraries get vendored. The patterns used, `libTFEL*`,
  `libMTest*`, `libMFM*`, `libMFrontQuery*`, `libMFrontLogStream*`,
  `libMFrontProfiling*`, `libMFrontGenericParallelRuntime*`, behave the
  same under both semantics and do not match MGIS's own
  `libMFrontGenericInterface*` (verified: `libMFM*`, not `libmfm*`, is the
  case of the actual library names).
- macOS: `delocate-wheel --require-archs {delocate_archs} -x <pattern> …`
  (`-x` is a regex).
- Windows: `repair-wheel-command = ""` (same reason as TFEL).

`test_wheel.py` greps the wheel content or relies on the version-agreement
check to catch a regression here (a vendored `libTFELMath.so*` inside the
MGIS wheel makes the check pass silently: the real guard is the exclusion +
a check that the wheel holds no TFEL library, added to `test_wheel.py`).

## 4. Changes required in MGIS

### 4.1 Allow overriding the python modules destination

`CMakeLists.txt` (lines 99-116) sets `MGIS_PYTHON_MODULES_INSTALL_DIRECTORY`
unconditionally; wrap the definition in `if(NOT
MGIS_PYTHON_MODULES_INSTALL_DIRECTORY)` so that the wheel can pass
`-DMGIS_PYTHON_MODULES_INSTALL_DIRECTORY=site-packages` (TFEL precedent:
`TFEL_PYTHON_SITE_PACKAGES_DIR`).

### 4.2 Fail when TFEL is required but absent or not the expected one

Next to `disable-tfel` (lines 224-234):

```cmake
option(require-tfel "fail the configuration if TFEL is not found" OFF)
set(MGIS_REQUIRED_TFEL_VERSION "" CACHE STRING
    "fail the configuration if the TFEL version is not this one")
```

With `require-tfel=ON`, `FATAL_ERROR` if `NOT TFEL_FOUND`, if
`MGIS_HAVE_MFRONT_SUPPORT` is off, if `TFEL_PYTHON_BINDINGS` is off, or if
`MGIS_REQUIRED_TFEL_VERSION` is non-empty and differs from `TFEL_VERSION`.
`setup.py` passes both; the normal build is unaffected. Add a job (or a
`check.yml` entry) exercising both outcomes.

### 4.3 Pip variant of `mgis/__init__.py`

The two existing variants only handle Windows DLL directories via
`MGISHOME` or a `../../../..` guess of the prefix — false in a wheel where
MGIS's libraries live inside the `mgis` module and TFEL's DLLs in the
sibling `tfel/bin`. Chosen mechanism (fewest cmake changes, TFEL
precedent): `setup.py` **post-processes the installed `__init__.py`**,
inserting after the `from __future__` statements a preamble which:

- sets `MGISHOME` to the module directory (so that a `mfront` launched from
  python finds MGIS's headers and libraries for `--interface=generic`),
- registers `mgis/bin` and `tfel/bin` with `os.add_dll_directory` on
  Windows (guarded by `os.path.isdir`, cf. lesson 3), the `tfel` directory
  being located with `importlib.util.find_spec("tfel")`,
- compares `importlib.metadata.version("tfel-mfront")` with the version
  baked in by `setup.py` and raises a clear error on mismatch
  (consistency layer 4; the `mfront.database` import of
  `__init__-have-tfel.py` keeps working unchanged).

### 4.4 pybind11-stubgen support (mirror of the reviewed TFEL PR #1083)

- `option(enable-pybind11-stubgen "generates stubs for python extensions"
  ON)` when `enable-python-bindings`, detection by `${Python_EXECUTABLE} -c
  "import pybind11_stubgen"` (lesson 1).
- `cmake/modules/mgis.cmake`: `set_property(GLOBAL APPEND PROPERTY
  MGIS_LIBRARIES ${name})` in `mgis_library()` (for the Windows DLL
  directories of the build tree, lesson 4).
- A new `cmake/modules/mgis-python-modules.cmake` (or directly in
  `bindings/python/src/CMakeLists.txt`, which currently defines
  `mgis_python_module`):
  - `mgis_python_module` sets `LIBRARY_OUTPUT_DIRECTORY` to
    `"$<1:${MGIS_PYTHON_MODULES_BUILD_DIR}/mgis>"` (or `mgis_<suffix>` when
    `MGIS_APPEND_SUFFIX`), so that the modules are next to the
    `__init__.py` of the package in the build tree (lesson 2 — MGIS does
    not set an output directory at all today: the modules go to
    `bindings/python/src/`, and the tests assemble a package by
    **symlinks** in `bindings/python/tests/mgis/`; the symlink assembly can
    stay as it is);
  - a `python_module_stubgen(target package name)` function registering
    `${target}:${module}` in a global property, called from
    `mgis_python_module` for `_mgis`, `behaviour`, `material_property`,
    `model`, `function` (respecting `MGIS_APPEND_SUFFIX` for the package
    name);
  - a `generate_python_stubs()` function, called at the end of the main
    `CMakeLists.txt` (after all `add_subdirectory`), generating with
    `${Python_EXECUTABLE} -m pybind11_stubgen <module> --output-dir
    ${MGIS_PYTHON_MODULES_BUILD_DIR}` a `python-stubs` custom target (ALL),
    installing the `.pyi` files next to the modules in
    `${MGIS_PYTHON_MODULES_INSTALL_DIRECTORY}`;
  - the build-tree package directory also gets a copy of the `__init__.py`
    variant selected at configure time (`file(CONFIGURE …)` /
    `configure_file`), as importing `mgis` runs it;
  - Windows: the generated `sitecustomize.py` (lesson 4) registers, in
    addition to the build-tree DLL directories from `MGIS_LIBRARIES`, the
    `bin` directory of the TFEL installation (from `TFELHOME`) so that the
    TFEL DLLs needed by `_mgis` are found.
- Install an empty `py.typed` marker in the `mgis` package (PEP 561;
  lesson 8 — coordinate with TFEL, which has agreed to do the same).

### 4.5 Relocatable cmake package (verification only)

`MFrontGenericInterfaceConfig.cmake.in` already resolves TFEL through
`TFEL_DIR` / `TFELHOME` / `$ENV{TFELHOME_<version>}` — the variable the
TFEL wheel sets at `import tfel`. Risk to check during implementation:
`install(EXPORT … EXPORT_LINK_INTERFACE_LIBRARIES)` may record absolute
TFEL paths from TFEL's own `Targets.cmake`. `test_wheel.py` runs a tiny
`find_package(MFrontGenericInterface)` project against the wheel's
`share/mgis/cmake` to prove it.

### 4.6 Versioned libraries

Contrary to an earlier reading of `cmake/modules/mgis.cmake`, the MGIS
libraries are **not** versioned: the `VERSION "${PROJECT_VERSION}"` there
only feeds `write_basic_package_version_file` (the cmake package version),
not the libraries. The installation holds a single unversioned
`libMFrontGenericInterface.so`, without soname version nor development
symlink, so the wheel layout has nothing to dereference and
`materialize_symlinks` in `setup.py` is only a safety net.

The TFEL libraries, on the other hand, have a *versioned soname*
(`libTFELMath.so.5.2.0-dev`): a mismatched `tfel-mfront` version manifests
itself as a dynamic linker error, which the check inserted in
`mgis/__init__.py` (and the `MGIS_REQUIRED_TFEL_VERSION` check of cmake)
report earlier and more clearly.

## 5. New files: `bindings/python/pip/`

- `pyproject.toml`:
  - `[build-system] requires = ["setuptools>=64", "cmake>=3.20",
    "pybind11>=2.12", "pybind11-stubgen>=3.0", "numpy>=2.0",
    "tfel-mfront==X.Y.Z", "patchelf; sys_platform == 'linux'"]`;
  - `[project] name = "mgis"`, `dynamic = ["version"]` (from
    `project("mfront-generic-interface" VERSION …)` of `CMakeLists.txt`,
    `-dev` → `.dev0`), `requires-python = ">=3.9"`,
    `dependencies = ["numpy", "tfel-mfront==X.Y.Z"]`; license CeCILL-C;
    `[tool.setuptools] packages = [] py-modules = []`;
  - `[tool.cibuildwheel] build-verbosity = 1`, `skip = ["*-musllinux_*"]`,
    `test-command = "python {package}/test_wheel.py"`, per-OS archs as in
    §2.3 and the repair commands of §3.
- `setup.py`: version pin guard + TFEL discovery (§2.2-2) + cmake
  configure/build/install with the options of §2.3 + `layout_package()`
  (copy `site-packages/*` at the wheel root, `bin`/`lib`/`include`/`share`
  into `mgis/`) + `__init__.py` preamble insertion (§4.3) +
  `set_relative_runtime_paths()` with the two rpath entries (§3) +
  `BinaryDistribution` (`has_ext_modules`) + the whole thing driven from a
  `build_ext` subclass (the only build command run when no python package
  is declared to setuptools).
- `test_wheel.py`, run by cibuildwheel in a fresh venv containing the
  built wheel (pip pulls the `tfel-mfront` dependency with it):
  1. `import mgis, mgis.behaviour, mgis.material_property, mgis.model,
     mgis.function, mfront.database` (the last one through `import mgis`),
  2. assert the TFEL version check passed and `mgis.behaviour` reports the
     expected `MGIS_HAVE_TFEL` features,
  3. assert no TFEL library was vendored into the wheel (§3),
  4. assert the `.pyi` stubs and `py.typed` are installed next to the
     modules (lessons 7 and 8),
  5. on non-Windows: write `Elasticity.mfront`, run the wheel's `mfront
     --obuild --interface=generic` (the `MGISHOME` and `TFELHOME` set by
     `import mgis` and the tfel launcher are inherited), load the library
     with `mgis.behaviour.Behaviour`, `mgis.behaviour.integrate` a uniaxial
     strain, check `S_XX ≈ 150e6` against the analytic result — the
     end-to-end consistency layer,
  6. on non-Windows: `cmake -find_package(MFrontGenericInterface)` on a
     tiny project against the wheel's `share/mgis/cmake` (§4.5).

## 6. New workflow: `.github/workflows/python-pip.yml`

Copy of TFEL's with the following deltas:

- triggers: push on the tags `MFrontGenericInterfaceSupport-[0-9]+.[0-9]+.*`
  (the repo's release tags have both `x.y` and `x.y.z` forms — confirm the
  convention for tagged wheel releases), push/PR on `master`, plus
  `workflow_dispatch` (release order: TFEL first).
- matrix `os x python` exactly as TFEL (cp39…cp315, cp312 on PRs).
- ccache: reuse this repo's `.github/actions/{setup,save}-ccache` — to be
  verified they expose the `key:` input and the `msvc.cmake` toolchain TFEL
  versions provide; MGIS's actions were built for the spack/OCI
  buildcache flows. One cache per OS (`key: wheel-<os>`), saved by the
  cp312 job; inside the manylinux container, static musl ccache via
  `CIBW_BEFORE_ALL_LINUX` (HTTPS only) and `CCACHE_DIR=/host<runner.temp>/ccache`.
- `pypa/cibuildwheel@v4.3.2`, `package-dir: bindings/python/pip`,
  `output-dir: wheelhouse`, `CIBW_BUILD: ${{ matrix.python }}-*`.
- artifact `mgis-wheel-${{ os }}-${{ python }}`.
- `publish-pypi` and `publish-github-release`, both
  `if: push && startsWith(github.ref, 'refs/tags/MFrontGenericInterfaceSupport-')`.

## 7. Open questions

1. **PyPI name**: `mgis` (available, recommended) vs
   `mfront-generic-interface`. Note that a `mgis` conda/pip ecosystem name
   clash, if any, is with an unrelated project only if one appears later;
   reserving it early is an argument for acting now.
2. **Tag convention** the publish jobs key on (see §6).
3. **Pin strictness**: `tfel-mfront==X.Y.Z` recommended for v1 (the TFEL
    wheel libraries carry a versioned soname, `libTFELMath.so.5.2.0-dev`,
    so an untested TFEL would fail to load obscurely rather than silently;
    the exact pin makes the failure explicit). Relax once the policy is
    proven.
4. **MGIS dev version wheels**: TFEL maps `5.2-dev` → `5.2.dev0`; the same
   mapping applies (`3.1.0` + `MFrontGenericInterfaceSupportDevelopmentVersion
   ON` → `3.1.0.dev0`). Dev MGIS wheels must depend on a published TFEL
   version, not a dev one (the pin is a PyPI requirement).
5. OpenMP OFF in the wheel (v1): accepted? (perf-sensitive users can build
   from sources.)
6. Shipping `include/` + `share/` in the wheel: recommendation is yes
   (cheap, keeps MGISHOME semantics identical to a normal install; needed
   for `mfront --interface=generic` from python, which is how the wheel is
   tested end-to-end).
7. `tfel-mfront` is **not on PyPI yet**: prototype against a locally built
   TFEL wheel (`pip wheel` of the TFEL clone, `--find-links` + a pinned dev
   version) until TFEL releases wheels; the PR job can even build the TFEL
   wheel first in a preceding job (escape hatch C of §2.1).

## 9. Findings of the local validation (against a simulated tfel-mfront)

The wheel was built and tested locally with `--no-build-isolation` against
a directory simulating the tfel-mfront wheel layout (a `tfel` package
holding `bin`, `lib`, `include` and `share`, plus a `tfel_mfront`
dist-info), then installed in fresh virtual environments, tested with and
without an `auditwheel repair`, with `LD_LIBRARY_PATH`, `PYTHONPATH` and
`TFELHOME` unset. Everything below was verified, not reasoned:

1. **The auditwheel excludes work and are necessary**: without them,
   `libTFELSystem-<hash>.so.5.2.0-dev` and friends are grafted into
   `mgis.libs/` of the MGIS wheel. The patterns are globs since auditwheel
   6 (`libTFEL*`, ...), cf. §3.
2. **The `tfel/lib` directory survives the repair of the tfel-mfront wheel
   itself**: repairing a simulated tfel-mfront wheel leaves the libraries
   with their original names in `tfel/lib` (auditwheel only grafts hashed
   copies of the libraries needed by the TFEL extension modules, and does
   not touch data files). The sibling relative runtime path of the MGIS
   wheel therefore always finds its TFEL, whatever repair policy TFEL
   chooses. (The default policy does make the TFEL wheel carry its
   libraries twice, and register two consumers of the same versioned
   sonames; worth reporting upstream, but harmless for MGIS.)
3. **The relative runtime paths are those of the installed layout**
   (computed in a simulated `site-packages`, cf. §3):
   `libMFrontGenericInterface.so` gets `$ORIGIN:$ORIGIN/../../tfel/lib` as
   `DT_RPATH`, the extension modules `$ORIGIN/lib:$ORIGIN/../tfel/lib`.
4. **The version guard fires**: with the metadata of the installed
   tfel-mfront changed, `import mgis` raises `RuntimeError: this mgis
   wheel was built against tfel-mfront 5.2.0.dev0, but version 9.9.9 is
   installed`, rather than failing later in the dynamic loader.
5. **The wheel is usable as a MGISHOME**: `test_wheel.py` compiles a
   behaviour with the `mfront` of the tfel wheel, integrates it through
   `mgis.behaviour` (exact value of the elastic stress), and builds a
   consumer project with `find_package(MFrontGenericInterface)` against the
   wheel, which loads the behaviour in C++ — for both the raw and the
   repaired wheel, in a clean environment.
