# Installing from source

These are generic installation instructions. Building from source
requires `cmake` (version 3.20 or later) to be installed
(<https://cmake.org/>).

## Overview

The simplest way to compile this package is:

1. `cd` to the directory containing the package's source code and type
  `cmake .` to configure the package for your system. This will build
  `MGIS` in place.

   However, we strongly recommend building `MGIS` out of the source
   tree as follows:
   
   - Create a `build` directory et go in this directory
   - Call `cmake <path_to_MGIS_SOURCES>` to configure the directory

   Useful options are listed below.

   Running `cmake` takes awhile.  While running, it prints some
   messages telling which features it is checking for.

2. Type `make` to compile the package.

3. Optionally, type `make check` to run any self-tests that come with
  the package.

4. Type `make install` to install the programs and any data files and
  documentation.

5. You can remove the program binaries and object files from the source
  code directory by typing `make clean`.

## Options

- `disable-tfel`: by default, `MGIS` tries to add support for `TFEL`,
  notably if `tfel-config` is found in the `PATH`. This option disables
  this behaviour.
- `enable-mgis-function`: enable or disable compilation of the `MGIS/Function` library.
  By default, compilation of `MGIS/Function` is enabled.
- `enable-mgis-function-precompiled-operations`: enable or disable compilation of
   some operations on basic functions. This options is only meaningful if `MGIS/Function`
   is enabled and if `TFEL` libraries are available.
- `enable-exceptions`: use exceptions to report contract violation and error reporting.
   By default, contract violation leads to abort the program.
- `enable-parallel-stl-algorithms`: enable the overloads of the
  `MGIS/Function` algorithms taking an execution policy of the standard
  library (default=ON). With `libstdc++`, this requires `TBB`: if `TBB`
  is not available, configure with `-Denable-parallel-stl-algorithms=OFF`.
- `enable-c-bindings`: compiles the `C` bindings (default=OFF)
- `enable-fortran-bindings`: compiles bindings for the `Fortran2003`
  language (default=OFF)
- `enable-python-bindings`: compiles the `Python` bindings. This requires
  the `pybind11` library and the `NumPy` headers to be available
  (default=OFF)
- `enable-fenics-bindings`: compiles the `FEniCS` bindings. Those
  bindings are experimental and very limited. To use `MGIS` with
  `FEniCS`, usage of the `Python` bindings are encouraged.
- `enable-julia-bindings`: compiles the `Julia` bindings. This requires
  the `CxxWrap` library to be available.
- `enable-website`: generate the TFEL website (enabled by default if
  pandoc is found)
- `enable-portable-build`: do not use processor specific flags.
- `enable-static`: compiles static libraries
- `enable-doxygen-doc`: enable the generation of the API documentation
  using with `Doxygen`. The documentation is generated by `make doc`
  and installed by a subsequent `make install`.

By default, the library tries to autodetect the TFEL libraries and
expects that a working version of TFEL is available in the
environnement. The `disable-tfel` option can be used to disable this
feature. The `TFEL_DIR` variable can be passed to `cmake` to help the
detection of the `TFEL` libraries: it must points to the `cmake` files
generated by the `TFEL` project.

## Sanitizers and hardening options

The sanitizers are supported with `gcc` and `clang` based compilers. The
`enable-sanitize-options` option takes the list of the sanitizers to
enable, for instance:

~~~~ {#sanitizers .bash}
$ cmake <srcdir> -DCMAKE_BUILD_TYPE=Debug -Denable-sanitize-options="address;undefined"
~~~~

As for any `cmake` list, the sanitizers are separated by semicolons. As a
convenience, commas may also be used as separators, which avoids to quote
the separator on some shells:

~~~~ {#sanitizers-comma .bash}
$ cmake <srcdir> -DCMAKE_BUILD_TYPE=Debug -Denable-sanitize-options=address,undefined
~~~~

The available sanitizers depend on the compiler and on its version. The
`address`, `thread` and `memory` sanitizers cannot be used simultaneously.
A sanitizer whose flags are rejected by the compiler or by the linker is
disabled with a `sanitizer '<name>' disabled` message.

Each sanitizer can also be enabled individually using the dedicated option
whose name is obtained from the sanitizer name:
`enable-<name>-sanitizer`, for instance:

~~~~ {#address-sanitizer .bash}
$ cmake <srcdir> -Denable-sanitize-options="undefined" -Denable-address-sanitizer=ON
~~~~

Such options can be combined with the `enable-sanitize-options` option: the
enabled sanitizers are the sanitizers listed in the `enable-sanitize-options`
option and the sanitizers whose dedicated option is enabled.

The flags of the sanitizers are added to the flags of the `C` and `C++`
compilers, unless `USE_EXTERNAL_COMPILER_FLAGS` is set: they shall then be
given in `CFLAGS` and `CXXFLAGS`. The test executables of the `fortran`
bindings are linked by the `fortran` compiler without those flags, and the
tests of the `python` bindings are run by an interpreter which is not
instrumented: with a sanitizer requiring a runtime library, such as
`address`, those tests fail at startup. With `gfortran`, the flags can be
passed to the `fortran` compiler, e.g.
`-DCMAKE_Fortran_FLAGS=-fsanitize=address`. Otherwise, those bindings
shall be disabled in such a build.

With `gcc`, the `undefined` sanitizer can be used directly:

~~~~ {#sanitizers-gcc .bash}
$ cmake <srcdir> -DCMAKE_BUILD_TYPE=Debug -Denable-c-bindings=ON \
    -Denable-sanitize-options="address;undefined"
$ make
$ ASAN_OPTIONS=detect_leaks=1 UBSAN_OPTIONS=print_stacktrace=1:halt_on_error=1 make check
~~~~

With `clang`, we recommend listing the checks of the undefined behaviour
sanitizer individually. `undefined` includes the `vptr` check, which
requires the executables to be linked by the `C++` compiler, so that the
tests of the `C` bindings fail to link, and the `function` check, which
reports every call to a behaviour or to a material property, as `MGIS`
calls them through pointers to functions declared with its own
structures. For instance:

~~~~ {#sanitizers-clang .bash}
$ CC=clang CXX=clang++ cmake <srcdir> -DCMAKE_BUILD_TYPE=Debug -Denable-c-bindings=ON \
    -Denable-sanitize-options="address;alignment;bool;bounds;enum;float-cast-overflow;float-divide-by-zero;null;object-size;return;shift;shift-base;shift-exponent;signed-integer-overflow"
~~~~

Some checks of the undefined behaviour sanitizer, such as
`integer-divide-by-zero` or `pointer-overflow`, have no dedicated option
and are thus not enabled by such a list.

An error detected by the address sanitizer makes the tested program exit
with a non zero status, and thus the test fail. By default, the undefined
behaviour sanitizer only prints its reports: the `halt_on_error=1` option
of `UBSAN_OPTIONS` makes it stop the program at the first report.

Note that passing a boolean value to the `enable-sanitize-options` option is
no longer supported: this option used to enable a set of sanitizers at once,
which is meaningless as most sanitizers cannot be combined.

The `enable-glibcxx-debug` option enables the debug mode of the standard
library of the GNU C++ library in debug builds. It can be combined with
the sanitizers, with two restrictions:

- `TFEL` must also be built with this option: this mode changes the
  layout of the containers of the standard library, which can't be
  exchanged between code built with and without it.
- With `gcc` (at least up to version 14), the `null` check of the
  undefined behaviour sanitizer (included in `undefined`) prevents the evaluation at compile time
  of the standard algorithms in this mode, which the unit types of
  `TFEL` require.

## `cmake` usefull variables

- `CMAKE_BUILD_TYPE`           : two values are supported `Release` and `Debug`
- `CMAKE_TOOLCHAIN_FILE`       : specify a tool chain file
- `Python_EXECUTABLE`          : path to the `python` interpreter to use
- `MGIS_APPEND_SUFFIX` and `MGIS_SUFFIX`: if `MGIS_APPEND_SUFFIX` is
  set, `MGIS_SUFFIX` is appended to the names of the libraries (for
  instance `libMFrontGenericInterface-${MGIS_SUFFIX}.so`), of the
  `python` and `julia` modules (where the characters `.` and `-` are
  replaced by `_`) and of the directories of the `cmake` packages, of
  the environment scripts and of the documentation, and the headers and
  the `fortran` modules are installed in `include/MGIS-${MGIS_SUFFIX}`.
  This allows several versions of `MGIS` to be installed in the same
  prefix.

# Installing using `spack`

`spack` is flexible package manager (https://spack.io/).

Installing `mgis` using `spack` shall be as easy as:

~~~~{.bash}
$ spack install mgis
~~~~

By default, the `c`, `python` and `fortran` bindings are installed. The
mgis package has numerous variants which allows customizing which
bindings must be built.

# Installing using `brew`

Installing `mgis` using `brew` shall be as easy as:

~~~~{.bash}
$ brew install mgis
~~~~
